# ANI BOSS Console API 对接流程

本文档约束 ANI BOSS Console 新增或调整接口时的契约核对、代码落位和验证流程。它不复制维护后端端点目录；迁移期以 `ani-governance` 为目标后端、`ANI` 为存量后端，具体路径、字段和行为始终回到对应权威后端的契约与实现核对。

## 契约核对

### 迁移期后端归属

`ani-governance` 与 `ANI` 是两套独立系统，接口契约与资源 ID 不兼容，不要求新接口兼容旧请求。当前处于后端能力逐步迁移、替代接口持续补充的阶段，不能假定新旧 API 同时可用。迁移以逐项补齐并核对 Governance 的正式能力为前提，不以旧接口作为新系统的兼容层或缺失能力的兜底；旧代码和契约仅作为迁移参考及待替换内容保留，其存在不代表旧服务仍可调用。权威后端的指定用于核对契约，不构成接口已部署、可联调或可跨系统使用的保证。

1. 已明确迁移的接口以 GitNexus 索引 `ani-governance` 为唯一权威实现；`ANI` 只用于迁移前后差异核对，不得以旧实现覆盖新契约。`ani-console` 已将密码登录及其 Cookie 刷新凭证语义列为已迁移范围；BOSS 平台身份接口仍须单独确认归属，不据此认定同步迁移。
2. 尚未明确迁移的接口仍以 `ANI` 为当前权威实现，同时查询 `ani-governance` 判断是否存在迁移实现；不得仅因目标仓库出现同名路由、模型或未完成代码就认定已经迁移或部署。
3. 两个后端的路径、字段、认证、幂等、错误或副作用存在差异，或无法确认接口归属时，必须停止相关对接并请用户确认，不得自行混用两套契约。
4. 后端尚未部署或用户明确禁止调用接口时，不得发送探测、联调或验证请求；只执行静态契约核对与前端检查，并在结果中列出未验证的运行时行为。

### Governance HTTP 接口约定

经 `ani-governance` 向前端提供的新增或修改 HTTP JSON 接口按以下规则核对。以下是对接约束，不代表 BOSS 对应接口已经迁移、部署或验证；具体端点仍按 Core 或 Services 流程查询权威索引。

#### 请求与响应

- 查询参数放在 URL 中，创建、修改的业务数据使用 JSON 请求体；业务字段及请求体结构以接口定义为准，不自行增删 `data` 包装。
- 普通详情直接返回资源对象，普通列表直接返回 `items/total`，不增加资源名称、外层 `data` 或统一的 `code/message/data` 成功包装。
- 写入需要返回单个资源时使用详情对象结构；无业务结果时返回 `{}`，`204` 不返回响应体。部分更新省略字段表示保持原值，清空必须显式表达；异步受理保留任务或操作信息，不把受理成功视为业务完成。
- 使用 HTTP 状态码区分成功与失败，不将失败包装成 `200`。错误体包含 `code`、`reason`、`message`，业务分支依据 HTTP 状态和 `reason`，`message` 仅用于说明。存在 `X-Request-ID` 或 `metadata.request_id` 时保留用于排查，不假定每个错误都具有请求 ID；前端统一通过[公共请求层](#公共请求层)处理。
- 64 位整数使用十进制字符串，时间使用 RFC 3339 字符串；字段名、枚举和其他类型按接口定义使用，不自行转换大小写或将所有 ID 转成数字。组合结果及列表的 `observation` 等元数据保留完整结构；导航树、权限或容量快照、统计和日志按业务结构处理，不因内部有数组就改成普通分页列表。

#### 列表分页核对

| 项目 | 必须满足的规则 |
|------|----------------|
| 请求参数 | 使用 `page`、`pageSize` 分页；`page` 从 `1` 开始，默认 `1`；`pageSize` 默认 `20`，范围为 `1` 到 `100` 的整数。两个参数分别使用独立默认值，页码上限、筛选与排序参数按具体接口声明核对。 |
| 参数校验 | 分页参数为单个规范十进制正整数；显式传入零、负数、空值、前导零、小数、重复参数或越界值必须返回 `400`，不得静默修正；未声明的查询参数也返回 `400`。公共查询数组序列化规则不代表分页参数允许重复。 |
| 响应结构 | `items` 为当前页数组；`total` 为当前调用者有权查看且符合筛选条件的实际总条数，JSON 类型为十进制字符串，不得用当前页长度冒充总数。类型声明保留字符串；展示或分页控件需要数值时直接使用 `Number(total)`，不额外添加合法性、非负或安全整数检查。 |
| 直接跳页 | 支持首次请求直接访问任意合法页，无需预先访问前面的页；不得使用游标循环或预拉取前页模拟页码分页。 |
| 空列表与超界页 | 无匹配数据时返回 `items: []`、`total: "0"`；页码超过最后一页时仍返回空数组，但保留实际匹配总数。 |
| 排序与一致性 | 后端先确定排序再分页，主排序相同时用唯一键兜底；列表与计数使用相同可信租户、权限和业务筛选范围，并在同一数据库只读快照读取。连续请求间数据可能变化，不将分页视为冻结结果。 |

不同领域保留各自明确声明的筛选、排序和授权条件，不直接套用 Console VPC 等特定资源的业务规则。

#### 不合规时中断与恢复

1. 对接新接口或修改 Governance 接口时，发现契约、实现或允许联调时的实际行为不满足上述约定，必须立即中断受影响的对接修改，先向用户说明具体接口、期望规则、实际差异、证据及对前端的影响；不得先实现兼容再补报，也不得通过字段重命名、响应拼装、伪造总数或遍历分页掩盖差异。
2. 只有相关问题已完成修改并重新核对符合约定，或用户明确确认绕过具体差异后，才能继续受影响的对接修改。明确绕过须记录确认范围、临时处理方式和仍未验证的事项，不将其他接口、其他差异或沉默视为一并授权；绕过上述约定不免除必需索引核对及禁止调用未部署接口等既有约束。
3. 中断时按[迁移标记与保留边界](#迁移标记与保留边界)保留旧实现和标记，不推进受阻实现；不能以添加标记代替用户明确确认。

### 迁移标记与保留边界

- 迁移阶段未迁移或迁移不完整的接口、字段、参数及关联组件、入口，以及因不合规中断的接口、类型或调用位置，必须在对应实现旁同时写明 `FIXME` 和 `TODO`，不得只在统一导出入口添加笼统标记。
- `FIXME` 写明未迁移或不合规的具体能力、字段、参数、影响及阻塞原因，说明保留旧实现或调用的原因，并记录用户明确确认的绕过范围（如有）；`TODO` 写明后端修正、前端契约对齐、迁移或验证事项及复核条件。
- 恢复对接后仍有差异或待验证事项时保留标记，完成修正并验证后才能移除；未部署或禁止调用时保留运行时验证 `TODO`，不得以静态核对替代联调结论。
- 已对齐部分按新契约接入；未对齐部分保留原组件、入口、请求契约及业务参数和旧调用，不得因公共组件迁移或新接口不合规而删除、隐藏或改变未迁移功能，也不得通过改名、类型断言或字段拼接伪装为新接口。旧接口文件与公开入口遵循[工程约定](./ENGINEERING-CONVENTIONS.md#废弃接口组织)。
- 保留旧实现和调用不授权将 Governance 资源 ID 交给旧接口、用旧详情补齐新资源字段，或在新接口失败、缺字段时自动回退旧系统。新系统未提供替代能力时按未完成迁移记录并保留 `FIXME/TODO`；同一资源的读写与关联必须遵循所属系统的正式契约，不能混合两套响应拼成已迁移功能。
- 用户明确指定迁移范围或标记例外时，按已确认范围执行；例如明确要求仅保留后期验证 `TODO` 的迁移项，不额外添加兼容分支或 `FIXME`。

### 资源创建、删除的 task 接口统一暂缓对接

- 所有资源创建、删除涉及的 task 查询、轮询及任务跟踪弹窗，本阶段统一暂缓对接，后续统一调整；在对应实现旁保留后续接入的 `TODO`。
- 异步创建、删除请求受理成功后，关闭提交弹窗（如有）、刷新相关列表并提示“创建已提交”或“删除已提交”；详情页删除提交后按既有交互返回。反馈渠道与结果语义遵循 [UI 开发约定](./UI-CONVENTIONS.md#用户反馈与请求状态)。

### Core API

1. 开始对接前，先使用当前会话接入的 GitNexus 工具查询索引 `ani-boss-console对接文档补充`，确认是否存在测试环境已部署、代码尚未合并期间的临时说明。
2. 按迁移期后端归属查询 `ani-governance`、`ANI` 或两者：在 `ani-governance` 核对 protobuf HTTP 映射、生成处理器、请求/响应模型、中间件及实现流程；在 `ANI` 核对 Core OpenAPI、网关注册、路由处理器、请求/响应模型及相关实现流程。
3. 后端已部署且允许调用时，联调核对测试环境的实际状态码、错误体、空响应、流式响应和副作用行为；否则执行静态核对并明确保留联调项。

未查询接口补充索引不得开始 Core API 对接。补充说明、权威后端契约与实现或测试环境表现存在差异时，不得自行选择其一或根据另一后端及前端旧代码推断，必须停止相关对接并请用户确认。

### Services API

1. 按迁移期后端归属查询对应后端索引，核对 Services OpenAPI 或 protobuf HTTP 映射、网关注册、路由处理器、请求/响应模型及实现流程。
2. 当前 `ani-boss-console对接文档补充` 的强制前置规则只针对 Core API；若查询命中与目标 Services 接口直接相关的补充内容，也必须纳入核对。
3. OpenAPI 已声明但网关未注册、实现尚未开放或测试环境行为不一致时，保持未接入或明确空态，并请用户确认后续口径。

前端不保留 Core 或 Services 的整份生成式 schema 快照。模块内 TypeScript 类型只提供编译期约束，不代表运行时校验，因此每次接口调整仍必须重新核对后端契约。

## 模块与类型落位

- 请求函数与接口类型统一放在 `src/api/<domain>/`；页面、路由、组件、Hook 和 Store 不得直接导入 Axios 或 `src/api/request.ts` 拼装平台请求。
- 简单领域使用 `index.ts` 与 `types.ts`；包含多个独立资源的领域按资源拆分文件或子目录，再由领域 `index.ts` 汇总公开接口。
- 页面提交类型命名为 `*Input`，不得携带幂等 key；API 内部最终请求类型命名为 `*Request`，并按后端契约加入 body 字段或请求 Header。响应、列表参数及资源记录使用具有业务含义的稳定名称。
- API 模块遵循[公共请求层](#公共请求层)的返回值和异常约定；查询返回查询结果，创建与操作提交按[创建与操作提交的返回值](#创建与操作提交的返回值)处理，不要求页面重复解包。
- 服务端请求状态、缓存和失效由页面组件中的 TanStack Query 管理；API 模块不持有 React 状态，也不包装或改变 `useQuery`、`useMutation` 的行为。
- 平台登录态位于 `src/components/auth/`，只使用 ANI 平台身份接口，不复用 Console 的租户登录字段。

### 创建与操作提交的返回值

- 普通资源创建流程及操作类 `POST`、`PUT` 提交默认丢弃响应体；业务 API 等待请求完成后返回 `Promise<void>`，调用方不解包、映射或依赖提交返回的资源、task 等数据。丢弃响应体不改变请求等待与异常处理。
- 提交成功后，通过对应列表或详情查询刷新资源数据，不依赖写入响应更新展示。

## 公共请求层

`src/api/request.ts` 对外提供以下公共能力：

| 能力 | 使用方式 |
|------|----------|
| Core API | `coreRequest`，基础路径为 `/api/v1` |
| Services API | `servicesRequest`，基础路径为 `/api/v1/svc` |
| 管理 API | `adminRequest`，基础路径为 `/api/v1/admin`，集中由 `ADMIN_API_BASE` 定义 |
| 外部预签名地址 | `externalAxios`，不安装平台认证拦截器 |

- `coreRequest`、`servicesRequest` 与 `adminRequest` 默认要求登录并注入平台访问令牌；只有登录、令牌刷新等公开端点显式传入 `auth: "public"`。
- 受保护请求返回 401 时由公共层执行单飞令牌刷新并重试一次；业务 API 和页面不得自行刷新令牌或重复实现 401 重试。
- 迁移期刷新凭证按权威契约传递：`ani-governance` 使用 `HttpOnly Cookie` 时必须启用凭证请求且不得把 Cookie 中的 refresh token 复制到前端状态或请求体；仍由 `ANI` 承载的旧链路可以继续使用其已声明的 body 字段。公共层必须兼容两种已确认契约，不得让业务页面判断后端来源。
- 公共请求层直接返回 `response.data`（HTTP 响应体），204 或空响应按 `undefined` 处理。业务 API 按用途返回查询结果或按[创建与操作提交的返回值](#创建与操作提交的返回值)丢弃写入响应，并通过异常报告失败；不要求页面重复解包，不引入 `{ data, error }` 双通道，Governance 普通响应体不再按内层 `data` 解包。
- 查询数组序列化为重复参数；`null` 和 `undefined` 不进入查询字符串。
- 请求失败统一转换为 `ApiError`，保留 `status`、`code`、`requestId`、`details` 和原始 Axios 请求/响应上下文，以及 Governance 契约中的 `reason`、`message` 信息。`ApiError` 是请求错误的唯一结构化模型；页面不得自行解析 Axios 错误结构，也不得新增 `ApiErrorAlert`、`showApiError`、列表错误通知 Hook、公开的通用错误解析对象或其他平行错误解析与反馈辅助函数。少数需要按契约中的状态或业务错误标识映射文案的场景，先判断 `error instanceof ApiError`；Governance 的判断依据遵循[请求与响应](#请求与响应)。
- 需要取消的请求透传 `AbortSignal`。Axios 取消保持为取消错误，以便幂等层识别并重置作用域。

## 幂等写请求

- 写请求是否要求幂等、以及 key 的传递位置严格以接口契约为准；需要幂等的操作统一由业务 API 模块管理，页面不得因请求用途自行跳过或补加 key。
- 每个要求幂等的独立写操作在模块作用域创建独立幂等作用域。固定依赖至少包含请求方法；不同写步骤不得共享作用域或 key。
- 页面先构造不含 key 的 `submitData`。影响请求身份但不在 body 中的稳定参数，例如资源 ID、文件指纹或操作类型，通过运行时依赖传入；路由模板和实际 URL 不作为依赖。
- 多数 Core 写请求使用 body 的 `idempotency_key`；租户 GPU 预留、GPU 集群切分等明确要求 Header 的接口使用 `Idempotency-Key`，不得自行改换载体或同时发送两份。本身为幂等替换且契约不接收 key 的租户配额 PUT 直接提交业务 body。
- 相同依赖和提交内容的普通失败重试必须复用 key；提交内容或依赖变化时生成新 key；请求成功或 Axios 取消时重置。
- 多阶段流程的每个写请求步骤使用独立作用域，不共享 key。
- DELETE 是否使用幂等 Header 或其他形式完全按后端契约处理，不得自行向 body 增加字段。

幂等 key 只能由公共幂等库通过外部 `uuid` 包生成。业务代码不得直接调用 `crypto.randomUUID()`、手工拼接 key、把 key 放入页面状态，或从页面重置幂等作用域。

## SSE 与预签名上传

- SSE 请求仍从对应业务 API 模块发起，使用 Axios fetch adapter、`responseType: "stream"` 和 `AbortSignal`，返回 `ReadableStream<Uint8Array>`。领域组件负责协议解析、去重、重连和界面状态。
- 预签名上传分为平台侧预约/完成请求与外部文件传输。平台请求继续使用 Core 或 Services 客户端并遵守幂等规则；外部地址只能使用 `externalAxios`。
- 外部预签名请求不得携带平台 JWT、平台 Cookie 或公共客户端默认 Header。只有后端契约为该上传会话返回的专用 Token、Content-Type 等 Header 可以显式加入。
- 外部传输错误通过公共错误转换函数归一化；需要支持取消的上传或轮询阶段必须复用调用方传入的 `AbortSignal`，不得在中途重新创建互不关联的取消作用域。

## 服务端筛选与分页

- 业务列表及关联选择器的搜索、租户范围、角色范围、排除条件、排序和分页统一由后端执行，后端返回与全部筛选条件一致的记录和总数。
- 前端只传递已核实的查询条件并展示结果；不得对接口结果二次筛选、截取分页、重算总数，或先查角色等关联资源再在前端求交集、拼接 ID 来补偿后端筛选缺失。
- 关联选择器必须关闭组件内置的本地选项过滤，搜索和排除条件发送到后端；树形关联应由后端处理排除自身及后代、避免循环等业务规则。
- 后端缺少所需筛选能力时，列出对应接口、组合条件、空结果及分页语义，交由后端完善契约；契约确认前默认保留未接入状态，不猜测参数或伪造空列表。用户明确要求先接入已有查询能力时，可暂用已核实的服务端条件，必须在对应代码添加 `FIXME`，说明缺失条件及当前数据范围，待后端支持后补齐；仍不得使用前端筛选补偿。
- 表单字段显示、只提交实际编辑字段等本地表单逻辑不属于接口结果筛选；可以保留。

### 分页与选项加载

- 禁止前端为本地筛选、分页、导出或下拉选项自动连续或并发拉取多个服务端分页并汇总为全量列表；API 模块、Hook 和组件均不得实现此类 `listAll*`、游标循环、递归或批量分页请求。普通分页列表每次只请求当前页，后续页由用户翻页或“加载更多”操作按需请求；全量能力应由后端提供明确接口。
- 新增或迁移的页码分页请求统一复用公共 `PageParams` 类型，按[列表分页核对](#列表分页核对)接入，不复制分散的分页类型。`cursor/limit` 仅供后端改造未完成的现有过渡调用保留，不作为新调用或示例，也不得通过参数转换包装成新契约。
- 当前阶段，下拉等选项数据临时仅取前 100 项，不代表全部资源，超过 100 项的选项暂不可见。支持 `page/pageSize` 的选项请求通过公共 `withFirst100` 包装已有列表函数，统一注入 `page=1`、`pageSize=100`，原样传递业务筛选参数、`signal` 和响应；接入时在 `src/api/pagination.ts` 集中提供该包装，不在调用方散写固定分页参数。
- 选项查询键保留业务用途与筛选条件，并通过 `options` 标识与普通列表分页区分；包装方法保留后续优化和移除固定分页策略的 `TODO`。选项不额外添加上一页、下一页或加载更多按钮，也不自动拉取后续页；此临时策略不改变普通表格分页及上述服务端筛选规则。
- 遇到或修改仍使用 `cursor/limit` 的过渡调用时，按[迁移标记与保留边界](#迁移标记与保留边界)注明保留原因和迁移条件，不据此批量改写尚未迁移的接口。

## 页面接入

- 查询和 mutation 通过 TanStack Query 调用领域 API 函数；mutation 只提交无 key DTO。反馈渠道、meta、稳定 ID、请求状态展示及错误呈现统一遵循 [UI 开发约定](./UI-CONVENTIONS.md)。
- 成功后由页面按资源关系失效或刷新查询缓存，API 模块不直接操作 Query Client。
- 页面、路由和组件中不得出现 `coreRequest`、`servicesRequest`、Axios 平台请求或幂等 key 生成逻辑；这些能力分别收敛在公共请求层和业务 API 模块。
