# ANI BOSS Console UI 开发约定

本文档是 BOSS UI 实现细则的唯一维护位置。页面信息架构、菜单和交互规格始终以 GitNexus 索引 `产品原型-9.11` 为准；目录、命名和路由适配遵循 [工程约定](./ENGINEERING-CONVENTIONS.md)。

## 实现顺序

新增或修改页面前，必须通过 GitNexus 查询 `产品原型-9.11` 中对应的菜单、路由和页面规格，不得根据现有前端页面反推产品要求。

新增或调整 UI 实现时，先检索当前项目的 `src/components/` 和同类型页面。按以下顺序选择实现方式：

1. 复用项目现有组件。
2. 使用 Arco Design React 的组件、属性和组合能力。
3. Arco 能力满足但外观不符时，通过公开的 `className`、`style`、Token 或主题能力局部调整。
4. Arco 无法满足时，使用 Tailwind CSS 完成布局、尺寸和间距，并封装为对应领域组件。
5. 仅当 Tailwind CSS 无法合理表达复杂选择器、伪状态或第三方组件内部覆写时，新增组件私有 CSS/LESS。

涉及第三方库 API、属性、类型或配置时，必须先按 `AGENTS.md` 使用 Context7 查询与当前依赖版本匹配的文档。

## 组件与样式边界

- 基础 UI 使用 `@arco-design/web-react`，图标使用 `@arco-design/web-react/icon`；不引入与 Arco 平行的组件库。
- 所有 Arco `Card` 统一无外边框、圆角 `8px`，由根级 `ConfigProvider.componentConfig.Card` 配置；业务侧不得覆盖为其他边框或圆角。此规则仅适用于 `Card` 组件。
- 不自行仿造 Arco 已提供的 Button、Form、Modal 等基础组件。
- 业务代码不得直接使用 Arco `Table`：普通组件、详情页和嵌入式表格使用 `DataTable`，标准列表页使用 `ListDataTable`。
- 需要展示的表格区块标题统一通过 `DataTable` / `ListDataTable` 的 `header` 配置，由内部 `DataTableSectionHeader` 子组件渲染标题、说明和右侧操作；不得使用 `Card.title` 或另写标题栏充当表格标题。`TableSectionFrame` 只负责表格区域布局、筛选和工具栏；是否保留区块标题仍遵循下文的页面标题去重规则。
- 颜色和状态语义优先使用 Arco Token；Tailwind CSS 主要负责布局、尺寸和间距。
- 状态和操作结果展示统一复用公共 `StatusBadge`，业务侧只维护文案与 `StatusBadgeTone` 的映射，不再用彩色 `span`、`Tag` 或另写同名组件重复实现；领域状态组件可以保留，但内部必须复用公共组件。日志级别、漏洞风险等级、事件类型和角色等分类标签不按状态机械替换。
- 全局范围谨慎使用 `Typography.Title`，不得仅为放大或加粗文字而使用。页面标题优先复用既有页面头部，普通强调文本使用 `Typography.Text`。确需标题语义时，必须通过局部 `className` 或 `style` 显式清除默认上边距，并明确设置下边距（如 `m-0!` 或 `mt-0! mb-4!`）；区块间距由父容器统一控制，避免默认 `1em` 上边距叠加或外边距折叠造成意外留白。此规则适用于所有页面、弹窗、Tab 内容和公共组件。
- 局部样式覆写限制在组件作用域内，不复制 Arco 源码，不污染其他页面。
- 页面壳层遵循顶部一级导航、左侧二级菜单与三级分组结构；侧边栏不重复展示当前一级菜单名称。
- 产品信息架构中的二级菜单对应侧边栏第一层，仅该层显示图标；侧边栏内部展开的第二层菜单不显示图标。
- 图表和数据可视化优先使用 `echarts-for-react`。

## 页面与组件组织

- 新页面先参考同类型已有页面，列表、详情和表单沿用已有公共骨架，不创建平行模板。
- 列表页、运营总览和其他常规页面统一通过 `ResourcePageFrame` 或 `ListPageFrame` 的 `header` 配置使用租户列表同款头部；`ResourcePageHeader` 作为 `ResourcePageFrame` 的内部子组件，不对外导出。页面标题只展示一次，页面只有一个主列表时，内容卡片不再重复“某某列表”等同义标题。仅当同页存在多个可独立描述的表格或区域时，才保留区块标题。详情页继续使用 `DetailPageFrame` 的详情头部。
- `ListToolbar` 中的搜索框和筛选项统一使用 Arco `Space` 组合，不为其中的 Arco 表单控件设置固定宽度。
- 页面级查询、状态、导航和组件组合放在对应页面组件中，可独立识别的复杂展示或交互区域继续拆为领域组件；路由入口职责与适配规则遵循 [工程约定](./ENGINEERING-CONVENTIONS.md)。
- 服务端状态使用 TanStack Query，跨组件客户端状态使用所属领域的 Store 或 Provider，组件局部 UI 状态使用 React 状态。
- 详情页中每个包含表格、布局块、条件分支、独立请求或交互流程的活动 Tab 内容必须拆为领域组件；已经直接引用现有业务组件的 Tab 不增加薄包装。被整段注释、等待接口开放的内容保持原状，不提前创建占位组件。
- 详情页 Tab 内容组件按实际业务功能命名，不使用 `Tab`、`Panel` 等容器后缀；目录和导出名遵循 [工程约定](./ENGINEERING-CONVENTIONS.md)。固定占位文案、空状态说明等由组件内部维护，不为其增加无复用价值的 props。
- 仅供某个 Tab 使用且不与详情页其他区域共享的查询、mutation、弹窗、确认框、局部状态和事件处理必须下放到该内容组件；详情页只保留跨 Tab 共享的数据与状态、顶层导航以及确需统一编排的操作，并通过明确 props 传递共享输入和回调。
- 详情页头部的资源级操作必须统一收纳在“更多操作”三点下拉菜单中，不在标题区平铺按钮或拆分主次操作；触发按钮使用竖向三点图标，并提供 `aria-label` 和 `title="更多操作"`。仅作用于某个 Tab 局部内容的操作保留在对应内容组件内，不提升到详情页头部。
- 包含动态列表、异步选项、字段联动或复杂校验的表单项，必须抽为可复用领域组件。
- 新建或改造的业务弹窗必须抽为以具体操作命名的独立领域组件，其 `Modal` 后缀、目录和导出名遵循 [工程约定](./ENGINEERING-CONVENTIONS.md)；页面、详情页和 Tab 内容组件不得内联承担完整弹窗 JSX。仅包含简短说明且没有表单、远程请求或独立状态的一次性确认可以直接使用 `Modal.confirm`。
- 弹窗的打开状态由调用方持有，并通过条件渲染挂载或卸载弹窗组件；弹窗组件内部的 Arco `Modal` 固定为可见，不得再接收或转发 `visible` prop。关闭后需要保留的状态必须有明确业务理由，不以常驻隐藏弹窗作为默认实现。
- 仅供弹窗使用的表单实例、字段校验、查询、mutation、pending 状态和事件处理必须收敛在弹窗组件内部；对外 props 只保留必要的业务输入、`onCancel` 和成功回调，不得绑定具体路由。固定标题、说明、按钮文案及空状态由组件内部维护，不增加无复用价值的展示型 props。
- 独立表格、弹窗、操作区或拥有自身状态流程的区域，拆为具有明确业务名称的领域组件。
- 原型中的编辑操作使用弹窗，并在用户确认后生效；不在详情展示区原地编辑或即时写入。
- 名称或主标识列已有详情跳转时，操作列不重复提供“详情”。
- 详情页左侧信息区作为资源概览，右侧 Tabs 不重复设置“概览”。

## 用户反馈与请求状态

- 业务代码不得直接调用 Arco `Message.*` 或 `Notification.*`；即时轻反馈统一使用 `src/lib/feedback.ts` 的 `showMessage`，查询、非表单操作和后台任务反馈统一通过 TanStack Query meta 或反馈模块声明。统一反馈模块只负责 Message、Notification 的展示与关闭。
- 所有用户可见查询必须配置 `meta.errorNotification`；确需静默的查询必须在查询定义旁注明原因。查询成功时由全局 `QueryCache` 关闭同 ID 的旧错误通知。
- 所有 mutation 必须配置 `meta.feedback`。表单提交使用 `channel: "message"`，非表单操作及后台任务使用 `channel: "notification"`；组件回调只保留缓存失效、关闭弹窗、导航等业务副作用。
- Query 与 mutation 的反馈 ID 必须使用短且页面无关的业务语义名称；同一数据源或同一操作在不同入口复用同一 ID，禁止包含文件路径、组件名或页面名。需要关联资源 ID 等动态维度时统一使用 `src/lib/id.ts` 的 `withId`；查询键等需要稳定作用域标识的场景复用同一工具。
- 数据列表的查询失败只通过统一 Notification 提示，不在列表区域渲染错误原因、Result、Alert 或错误专用重试按钮。
- 列表、表格无可展示数据时统一使用组件既有空占位，包括首次查询失败；不得为错误状态增加 `loadFailed`、`failed`、空白壳层或额外条件包装。后台刷新失败且已有缓存时继续展示缓存数据。
- 表单控件具有可识别标签，校验错误显示在相关字段附近；提交校验失败还必须显示一次统一 Message，接口提交成功或失败也使用 Message；直接调用 `form.validate()` 时必须经过统一校验入口，避免漏提示或重复提示；用户确认前不得提交修改。
- 非表单操作和后台任务使用 Notification；loading 通知常驻，并通过同一稳定 ID 更新为成功或失败。复制、无变化等即时轻反馈使用 Message。
- 资源自身业务状态（包括名为 `error` 或 `failed` 的状态值）及静态说明、风险提示类 Alert 不属于远程请求错误提示，不得机械删除。

## 组件拆分判断

文件行数用于提示职责是否过多，不作为机械拆分目标：

- 路由文件建议控制在 150–300 行，职责限定为路由参数处理、页面状态编排和组件组合。
- 业务组件通常控制在 80–200 行；超过 250 行时，应检查是否承担了多个可独立描述的职责。
- Hook 或状态逻辑超过 80–120 行，或包含多组相互独立的操作流程时，应考虑按业务流程抽取。
- 单文件页面超过 500 行时，通常应拆分；仅当内容高度线性、职责单一且拆分不能降低理解成本时可保留。

满足以下任一条件时，应优先拆为具有明确业务名称的领域组件或 Hook：

- 页面区域具有独立标题、表格、弹窗或完整交互边界。
- 某一区域拥有独立状态、事件处理和操作流程。
- 可以使用明确的业务名称描述，例如“设备表”或“租户分配台账”。
- 页面主体或 UI 片段被两个及以上路由复用。
- 需要单独维护、测试，或已存在明确的复用需求。
- 修改某一区域时，经常需要在同一大文件的不同位置之间来回查找。
- `useState`、事件处理函数或表格 `columns` 按业务区域明显成组出现。

拆分时应让新组件或 Hook 承担完整、可命名的业务职责，并尽量由其内部管理相关状态与操作，避免将实现细节重新变成大量零散参数传递给父组件。

以下情况不应仅为缩短文件而拆分：

- 只有十几行、没有独立业务语义的 JSX 片段。
- 仅转发一层 props、未隔离状态、逻辑或复杂度的薄组件。
- 拆分会引入大量零散参数、使状态归属模糊或增加跨文件跳转成本；此时应保留在原组件中，或先重新划分职责边界。

## 交互底线

- 危险操作必须二次确认，并明确操作对象与影响。
- 保留 Arco 默认键盘操作和焦点样式；纯图标操作提供可访问名称或可见提示。
- 长文本、资源 ID 和表格内容不得破坏布局；截断时提供查看完整内容的方式。
- 空值占位统一使用半角连字符 `-`，不得使用长破折号 `—`。
- 以桌面端为主要场景；表格过宽时允许横向滚动，并保留关键标识与操作。
- 表格操作列使用满足按钮内容的明确宽度，不使用 `max-content`；否则在表格内容较少、剩余空间较多时，操作列可能被完全撑开。
- 尚未接入后端的能力使用明确演示状态、禁用态或空态，不伪造接口成功结果。
